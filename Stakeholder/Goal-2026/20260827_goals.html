DETAIL 01方案已定

广告追踪与付费分析

Adjust 结论、待验证问题与 CID + Token 实施链路
当前结论台湾团队遗留的 Adjust 接入无法稳定覆盖广告到付费的完整归因；旧方案评估已完成，自研方案已确定，下一步进入开发。

开发前需要关闭的验证项

范围目前情况需要关闭的问题
Adjust已有 Install、Register、Purchase。确认 Purchase 是仅首次付费触发，还是每次付费／续费触发；查明 Adjust 与后台付费数据落差。
Landing / Backend广告进入 /landing/ 后，后台无法稳定带入推广人；部分 APK 安装会丢失推广人，重装时曾带入测试推广码。移除不可靠的推广人继承方式，以唯一 CID 和 Token 建立确定关系。
付费周期后台尚未直接提供完整归因周期统计。提供 1D、3D、7D、14D、30D 内完成首次付费的统计。
暂不纳入Meta Pixel、Facebook Event、AppsFlyer 当前未用于投放。本阶段不开发；GTM 事件继续由广告运营侧管理，需要代码改动时再提需求。

下一步实施方案

1 · 页面生成 CID载入页面时只生成一次，并在整个页面会话复用。
2 · 首次点击下载按钮立即禁用或防抖，只发送一次带 CID 的下载请求。
3 · 后端幂等处理按 CID 查询归因记录；存在则复用，不存在才创建，CID 设唯一索引。
4 · Token 绑定后端生成唯一 Token，与本次 APK 下载及 CID 归因记录绑定。
5 · 贯穿业务事件安装、注册、首次付费、续费及金额回传同一归因链路。
方案结果页面重复点击不会增加请求；MIUI 或 Android DownloadManager 重试仍携带同一 CID。系统重试不可完全避免，但后端复用同一归因记录，不重复计算访客。
设计边界不增加生成 CID 的 API，不依赖 IP／User-Agent 推测，不使用重定向技巧，也不针对特定 OEM 写例外逻辑。

API + AI 浏览器 Agent 混合采购建议
供应商类型执行方式必要控制
有完整 APIBO 直接查询库存和价格，创建 VM／IP，取得访问资料，并执行续费、取消、重启或重建。供应商、区域、规格及金额白名单；幂等键防止重复购买；失败自动重试。
只有部分 APIAPI 负责现有 VM 生命周期；缺少的购买或付款步骤交给 AI 浏览器 Agent，再回到同一 BO 采购任务。每一步保存状态；API 与浏览器不能同时重复执行同一订单。
无 API／无 Top Up使用 OpenClaw 类受控浏览器 Agent 登录供应商网站、选择批准的套餐和区域、建立新订单；不能 Top Up 时购买新的已批准 SKU。首阶段付款前人工确认；2FA／验证码转人工；限制单笔、每日及每月金额；保存页面证据、订单号和账单。
AI 自动采购目前是建议方案，不是已完成能力浏览器页面会改变，也会遇到库存变化、登录过期、2FA、验证码及付款失败。AI 应作为 BO 的一种供应商驱动，由 BO 控制预算、状态、审计和重试；不应让 Agent 自由决定供应商、规格或金额。
