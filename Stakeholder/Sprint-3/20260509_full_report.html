2026年5月9日 · 第3阶段提前收官（4/27–5/9）· 稳定测试版 v3.7.0 进入最终 QA
TL;DR · 一句话
Arrowfish 安卓 v3.7.0 稳定测试版进入最终 QA — 是接手项目以来第一个由本团队完整把控的稳定基线（前期 V3.2.0 / V2.0.0 测试单合并复验主体已通过；最终 QA 通过即发布生产）。后端发布提速 4–6 倍，节点开通由 SSH 手工 20 分钟降至后台一键 30 秒。第3阶段以「稳定基线定型 + 节点配置就绪」作为关门标准提前收官；FFF Flutter 重写与基础设施加固（数据库异地备份 / 网络隔离）锁定第4阶段 P0 优先级。下一里程碑：v3.7.0 最终 QA 通过 → 生产发布 + 第4阶段 5/12 启动。

收入保护

影响金额估算（保守）：本阶段修复的两个 P0 收入路径合计影响所有月续订用户的第二个月生效与免费注册路径。具体金额数据需要 1-2 周财务侧对账确认；初步评估：续订代币推进修复直接关闭了「客户已扣款但 VIP 没生效」的客诉来源 — 在以前的回执路径下，这类客诉每月以个位数比例出现并需要客服一对一退款。

合规姿态

  • 滥用观察检测器以无日志方式实现 — 节点端单向哈希源 IP，仅计数上报后端；后端不持有任何原始 IP — 是「无日志合规」与「滥用治理」共存的范式样板
  • 跨端可追溯日志（关联 ID）不涉及用户访问内容、目的地、流量元数据 — 仅用于「错误诊断」
  • 14 天数据保留策略纳入两个新增表（节点用量 / 异常计数）

后端改动的特殊挑战（多客户端兼容约束）

本阶段后端发布需要同时服务以下客户端，其中两个已冻结、不能要求其升级：

  • Android（可升级） — 主流量端，本阶段升级至 v3.7.0（最终 QA 中）
  • iOS HiYou v1.3.0（已冻结） — Apple 账号封禁导致无法发版；后端必须保持向后兼容
  • Windows skytree_pc v2.2.71（已冻结） — 签名证书过期；后端必须保持向后兼容

由此，本阶段每个后端改动都需要额外的「不破坏老客户端」的设计与测试成本（估计 ~30% 设计与测试开销加在每张工单上）。本阶段未发生因后端改动导致 iOS / Windows 失效的事件 — 兼容性纪律保持。

解锁路径（运营 / 商务侧议程）：

  1. iOS 账号申诉恢复 — 才能让冻结版本退役
  2. Windows 虚拟签名方案调研 — 才能让冻结版本升级

这两项推进越快，后端越早能从兼容约束中解放，FFF 重写也越容易共享后端代码（现在 FFF 后端默认从 Arrowfish 后端分叉）。

十三、为什么必须先清理技术债

第3阶段把产能优先放在共用后端基础平台而不是直接启动 FFF 重写，关键判断是：

  1. FFF 后端是 Arrowfish 后端的分叉 — 任何在 Arrowfish 后端今天清理掉的技术债，FFF 不需要再清理一遍
  2. 关联日志、协程崩溃保护、Swagger 自动文档、共享日志模板、多语言字段这些基础设施越早进 main 分支越便宜 — 多客户端跨调试、多支付通道、多语言上线都是 FFF 的天然需求
  3. 节点运维自动化是 FFF 上线的硬依赖 — FFF 也需要节点；如果节点开通仍是手工，FFF 上线时会再次面临中国封锁应对的人力瓶颈
  4. 第3阶段的安卓稳定 v3.7.0 是「我们能交付稳定版」的对外信号 — 接手以来第一个本团队完整把控的稳定基线（最终 QA 通过即发布生产）；这是 FFF 商务侧合规材料的产品依据

反过来说：如果第3阶段先启动 FFF Flutter 重写，要么会从一个尚未清理的后端分叉（继承 Arrowfish 所有遗留债），要么会让 Arrowfish 进入与 FFF 长期分叉但都没修好的状态。先清债再开新分支是更高效率的顺序。

HEAD 的代码净行数比 v1.7.38 少了约 1 万行（+19,274 / −30,236 行 / 1,123 个文件）— 方向是清理为主、新增为辅。

  • 可读性：构建脚本注释化简（430 → 370 行）；后端配置缓存改为单原子指针，单行替代了原本散落的锁；登出时序统一收口到入口活动；倒计时显示规则单一所有者，消除原本的视觉抖动；网络监控类合三为一（删掉两个旧实现）。
  • 翻译混乱大清理：接手时数据库存在大量「中英文混用」「[EN] / (簡) 临时占位符」遗留行，前端会偶发显示原始模板（{{plan_name}}）。本阶段在后端写入路径加了语言守门（写入时拒绝错误语言的内容）+ 三种语言（zh-CN / zh-TW / en-US）在 10 张可翻译表上一次性补齐 + 历史脏数据迁移清理。下载页也按语言切换严格分离，不再有同一渲染里出现中英混用。

之前管理后台前端编译错误（如 i18n 重复键）会拖垮整个后端流水线；现已拆分，互不影响。

无日志合规承诺

本阶段对所有新增的后端日志路径做了无日志合规审查。滥用观察检测器采用「源 IP 在节点端单向哈希、仅计数上报后端」的设计 — 后端拿到的是「同一 UUID 在多少个 IP 上出现」这一计数，没有任何原始 IP 落地。这是新增能力进入生产前的合规默认姿态。

无日志合规仍待加固（第4阶段并行）

  • 节点系统日志 — 关闭 rsyslog / journald 的持久化（依节点角色按需保留），避免系统层面意外留下流量元数据
  • SMTP 端口阻断 — 节点出口阻断 25 端口
  • Ansible 配置完整性 — 节点配置以代码形式管理
  • FFF 后端从第一天开始不写任何日志 — 第3阶段已搭好基础设施层；FFF 第4阶段直接享用

跨端可追溯日志（不涉用户行为）

所有 API 调用都有一个唯一关联 ID，从客户端发出到后端处理到节点接收，整链路可串联。仅用于「错误诊断」用途；不记录用户访问内容、目的地、流量元数据。客户端崩溃时直接关联到后端那一次请求；后端日志按 ID 检索就能看到同一客户端的请求序列。

无日志承诺的对外宣传时机

v3.7.0 生产发布建议只主推「稳定 + 可靠 + 速度」三个产品要点；「无日志承诺」等到第4阶段节点系统层加固完成后再统一对外发布。具体材料语言待第4阶段一并定稿，避免出现宣传与实际节点状态之间的差距。FFF 上线前的合规白皮书也按这个节奏。
