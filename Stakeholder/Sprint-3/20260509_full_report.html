七、USDT 支付通道：从台湾团队遗留 Java 黑盒 → 团队自有 Go 服务

  • 任何 bug 修复都要先完整反编译 → 找改动点 → 改完源码 → 重新编 jar → 部署，链路长且容易出错

  • 没有 CI 构建产物可追溯；没有源码评审；没有标准 systemd 管控（靠 PM2）

WoSign 详细说明

  • 当前签名证书形态：WoSign 实体 USB Token（物理设备代码签名）— 团队接手时证书已过期，无法签出新的可信 Windows 安装包
  • 需要做的事（按估时排序）：
    1. 研究 WoSign 续签流程与现行成本（实体证书签发周期通常 5-15 个工作日）
    2. 迁移到云代码签名（Cloud Code Signing：Azure / GCP / DigiCert KeyLocker / SSL.com 等）— 不再依赖物理 Token，CI 可自动签名；但需要重新走 EV 验证流程（机构身份核验 1-3 周）
    3. 过渡期内积压的 Windows 端 bug 修复无法发布
  • 云签的副作用：CI 可签 = Windows 也能像 Android 一样自动化发版，但首次成本（验证流程）短期不可省略

  • 需求侧的「这个能不能改」会议变多 — 接口契约改动需要先确认是否影响冻结版本
  • API 版本化负担 — 一些改动只能走新版接口，老版本不能动 — 维护两套实现的隐性成本
  • 知识依赖 — 团队必须维护对 v1.3.0 / v2.2.71 行为的精确认知（内部已审计 38/39 接口的向后兼容性）

九、持续交付与 AI 协作（多线工程并行的工作流）

本阶段除了交付的具体特性，还有一项「过程层」的产出：让多个工程方向能并行推进而互不阻塞，并且把 AI 编码助手（Claude Code）以可审计的方式嵌入到日常流程里。这是接下来 FFF 与 Arrowfish 同步推进所必需的工作模型。

统一的 Git 流（写在仓库规则里）

  • 分支命名规范：fea/（功能）、enh/（增强）、fix/（缺陷）、hot/（热修）、ref/（重构） + 短横线连字符的简短描述
  • MR 标题即 Release Note：用 Add / Fix / Update / Remove / Improve 做前缀，72 字符内；标签 feature / enhancement 进入「新功能」段，bug / fix 进入「修复」段
  • 分支从 main 拉，合并前 rebase，合并后本地 + 远端清理；一个 MR 只解决一个关注点
  • main → 测试环境，打版本 tag → 生产环境：没有意外的自动部署，发布是显式的

AI 协作如何嵌入（不是黑盒）

  • 技能（Skills）是项目专属的工作流：/plan（每个任务的计划与设计）、/commit（生成符合 Release-Note 规范的 MR 标题与标签）、/code-reviewer、/db-study（只读的生产 DB 查询）、/api-spec（移动端契约差异）、/knowledge-base-updater（沉淀新发现）。这些技能定义在 .claude/skills/ 里，像代码一样走 MR 评审。
  • 规则（Rules）是每个会话都加载的硬约束：原则 / Git / 安全 / 日志 / 数据访问 / Sprint 工作流 / 模型选择 / 效率，加上按文件类型限定的语言规范（Go / Kotlin / Flutter）。技能引用规则，但不重复规则的内容。
  • 知识库（Knowledge Base）记的是「事实」而不是「决定」：DB 表结构片段、生产 IP、踩过的坑。新发现统一通过 /knowledge-base-updater 入库，下一个动同一区域的人不必再发现一遍。
  • Token 纪律是规则而不是口号：rules/general/efficiency.md 强制「能用 2-3 个 grep / read 解决就别开 sub-agent」；默认主模型走 opusplan（Opus 规划 / Sonnet 实现），sub-agent 必须显式标 model — 这把 AI 协作的成本控制在合理范围内。
  • 会话钩子自动跑工作区初始化（符号链接、MCP、索引），不需要人工敲 /start。

这套工作模型为什么对第4阶段重要

  1. FFF 启动后 Arrowfish + FFF 双线并行，对分支隔离与计划范围管理的要求会更高；本阶段的 git-flow + 计划文件流程已经是经过实战的工作系统
  2. 后端兼容矩阵（iOS HiYou v1.3.0 + Windows skytree_pc v2.2.71）持续抽税，每个改动都需要在多客户端上跑兼容验证；MR 标题规范 + 计划文件让多人评审在不丢上下文的情况下高速运转
  3. 知识库的复利：本阶段沉淀的 DB schema、节点防火墙策略、CI 踩坑等知识进入仓库后，下一阶段做同领域工作时 Claude 直接基于这些事实决策，不会重新发现一遍
  4. 所有 AI 协作流程对内可审：技能、规则、提示词都是仓库内文件，新人 onboarding 看到的是同一份系统

十五、为什么必须先清理技术债

第3阶段把产能优先放在共用后端基础平台而不是直接启动 FFF 重写，关键判断是：

  1. FFF 后端是 Arrowfish 后端的分叉 — 任何在 Arrowfish 后端今天清理掉的技术债，FFF 不需要再清理一遍
  2. 关联日志、协程崩溃保护、Swagger 自动文档、共享日志模板、多语言字段这些基础设施越早进 main 分支越便宜 — 多客户端跨调试、多支付通道、多语言上线都是 FFF 的天然需求
  3. 节点运维自动化是 FFF 上线的硬依赖 — FFF 也需要节点；如果节点开通仍是手工，FFF 上线时会再次面临中国封锁应对的人力瓶颈
  4. 第3阶段的安卓稳定 v3.7.0 是「我们能交付稳定版」的对外信号 — 接手以来第一个本团队完整把控的稳定基线（最终 QA 通过即发布生产）；这是 FFF 商务侧合规材料的产品依据

反过来说：如果第3阶段先启动 FFF Flutter 重写，要么会从一个尚未清理的后端分叉（继承 Arrowfish 所有遗留债），要么会让 Arrowfish 进入与 FFF 长期分叉但都没修好的状态。先清债再开新分支是更高效率的顺序。

无日志合规承诺

本阶段对所有新增的后端日志路径做了无日志合规审查。滥用观察检测器采用「源 IP 在节点端单向哈希、仅计数上报后端」的设计 — 后端拿到的是「同一 UUID 在多少个 IP 上出现」这一计数，没有任何原始 IP 落地。这是新增能力进入生产前的合规默认姿态。

无日志合规仍待加固（第4阶段并行）

  • SMTP 端口阻断 — 节点出口阻断 25 端口

跨端可追溯日志（不涉用户行为）

所有 API 调用都有一个唯一关联 ID，从客户端发出到后端处理到节点接收，整链路可串联。仅用于「错误诊断」用途；不记录用户访问内容、目的地、流量元数据。客户端崩溃时直接关联到后端那一次请求；后端日志按 ID 检索就能看到同一客户端的请求序列。

无日志承诺的对外宣传时机

v3.7.0 生产发布建议只主推「稳定 + 可靠 + 速度」三个产品要点；「无日志承诺」等到第4阶段节点系统层加固完成后再统一对外发布。具体材料语言待第4阶段一并定稿，避免出现宣传与实际节点状态之间的差距。FFF 上线前的合规白皮书也按这个节奏。
